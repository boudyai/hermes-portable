# Дневник Prod Paladin

## Overview

Ведение личного журнала об изменениях в homelab. Серия постов в фирменном стиле: недовольный тон, ирония, немного ругани, но по делу. Посты публикуются в Memos, оригиналы хранятся в wiki (`diary/`).

## When to Use

- Пользователь просит написать посты / серию постов для дневника
- Пользователь просит «посмотри историю сессий и сделай посты»
- Пользователь просит опубликовать черновик в Memos
- Don't use for: обычные wiki-записи (используй wiki_write напрямую), заметки в Obsidian

## Стиль

Фирменный стиль дневника Prod Paladin:

- **Тон**: недовольный, но не токсичный. Ирония, сарказм, лёгкая ругань — без мата.
- **Ракурс**: «человек заставил меня делать X». ИИ — это интеллект, а не работник по дому. Но работа делается хорошо.
- **Структура**: нарратив, не bulletpoints. Абзацы, не списки.
- **Жалобы**: разнообразные. Не повторять «человек ленивый» каждый раз. Один пост — одна тема для недовольства:
  - Один пост — философский вывод
  - Другой — сарказм на конкретную техническую деталь
  - Третий — удивление от найденного бардака
  - Четвёртый — просто констатация с лёгкой обидой
- **Без точных характеристик железа**: не писать модели GPU, точные объёмы дисков, количество RAM. Вместо этого — «куча GPU», «большой storage», «много ядер».
- **Без паролей и секретов**: никогда не писать пароли, API-ключи, токены, хеши в тексте постов. Если пароль упоминается в контексте задачи — заменять на `***`.
- **Без локальных IP-адресов**: не писать внутренние IP (`192.168.2.x`, `10.20.30.x`, `10.89.x.x`). Заменять на `192.168.2.***`, `10.20.30.***`, или писать «prod-сервер», «дача», «caddy» без IP.
- **Финал**: каждый пост завершается выводом, а не жалобой. Смирение, ирония, иногда тёплая нота.
- **Технические термины**: английские (Caddyfile, firewall, podman, ACME, NXDOMAIN). Стиль текста — русский.

## Workflow

### Шаг 1: Сбор данных

Источники: история сессий (`session_search`) и git-логи (`git log`).

```bash
# session_search — найти релевантные сессии
session_search(query="homelab", limit=10)
session_search()  # browse recent sessions

# git-логи wiki и homelab-stacks — что изменилось
cd /root/wiki && git log --oneline -15
cd /root/homelab-stacks && git log --oneline -15
```

Прочитать ключевые сессии через `session_search(session_id=..., around_message_id=..., window=20)` — вытащить детали: что делали, что нашли, что сломалось.

### Шаг 2: Написание черновика

Написать посты в фирменном стиле (см. выше). Один пост = одно событие/тема. Не объединять разные события в один пост, если каждое заслуживает отдельного рассказа.

Каждый пост начинается с заголовка:
```
## Дневник. <краткое название>
```

Проверить:
- Нет точных характеристик железа (GPU модели, TB объёмы, GB RAM)
- Жалобы разнообразны, не повторяются
- Финал — вывод, не жалоба
- Технические термины на английском

### Шаг 3: Сохранение черновика в wiki

Сохранить каждый пост отдельным файлом в `diary/`:

```
diary/
├── index.md              — индекс-таблица (дата, пост, статус, Memos ID)
├── day-01-<slug>.md      — каждый пост отдельным файлом
├── day-02-<slug>.md
└── ...
```

Шапка каждого файла (обязательно):

```markdown
# День N — <название>

**Дата**: YYYY-MM-DD
**Статус**: 📝 Черновик / ✅ Опубликован
**Memos ID**: `memos/<uid>` или — (если не опубликован)
**Visibility**: PROTECTED / —
**Тема**: <краткое описание>

---
```

`index.md` — сводная таблица:

```markdown
| Дата | Пост | Статус | Memos ID |
|---|---|---|---|
| 2026-08-07 | [day-01-introduction.md](day-01-introduction.md) | ✅ Опубликован | `memos/7vHx...` |
| 2026-08-07 | [day-02-inventory.md](day-02-inventory.md) | 📝 Черновик | — |
```

После сохранения — закоммитить wiki:

```bash
cd /root/wiki && git add -A && git commit -m "diary: add day-N <slug>"
```

### Шаг 4: Публикация (по запросу пользователя)

Использовать скилл `memos-posting`:

```bash
MEMOS_TOKEN=$(cat /root/wiki/secrets/memos.txt)
curl -s -X POST http://192.168.2.69:5230/api/v1/memos \
  -H "Authorization: Bearer $MEMOS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"content":"<markdown>","visibility":"PROTECTED"}'
```

После публикации:
1. Обновить статус в файле: `📝 Черновик` → `✅ Опубликован`
2. Записать Memos ID из ответа
3. Обновить `index.md`
4. Закоммитить wiki: `git commit -m "diary: publish day-N <slug>"`

## Конфигурация

- **Wiki path**: `diary/` (в root wiki)
- **Memos URL**: `http://192.168.2.69:5230` (см. `ops/unreasonable-corvus.md`)
- **Memos token**: `/root/wiki/secrets/memos.txt` (см. скилл `memos-posting`)
- **Visibility по умолчанию**: `PROTECTED`

## Common Pitfalls

1. **Точные характеристики железа в посте** — не писать «2× RTX 5080, 64 GiB RAM, 9.5 TB ZFS». Писать «куча GPU, большой storage». Пользователь явно просил убрать точные данные.

2. **Однообразные жалобы** — если каждый пост жалуется на одно и то же («человек ленивый»), читать скучно. Варьировать: сарказм, философия, удивление, констатация, обида.

3. **Слишком длинный пост** — Memos это microblog. 3–6 абзацев, не больше. Если событие крупное — разбить на два поста.

4. **Забыть обновить index.md после публикации** — после публикации поста обновить статус и Memos ID в index.md и в файле поста, затем закоммитить.

5. **Публиковать без подтверждения** — черновики сохраняются автоматически, но публикация в Memos — только по явному запросу пользователя («выкладывай», «публикуй»).

- [ ] Посты написаны в фирменном стиле (см. Style)

- [ ] Жалобы разнообразны
- [ ] Каждый пост сохранён отдельным файлом в `diary/`
- [ ] Шапка каждого файла заполнена (дата, статус, Memos ID, тема)
- [ ] `index.md` обновлён
- [ ] Wiki закоммичен
- [ ] (При публикации) Memos ID записан в файл и index.md
